# 知识速查手册 skill（暂名）

- 创建：2026-10-11
- 线索来源：用户 2026-10-11 提出的第一个任务，原始表述见「一、要解决的问题」

## 一、要解决的问题

用户要快速、系统地入门某类知识时，希望一次性获得包含知识地图、核心理论、重要概念与关键词、重要历史发展节点等内容的结果，既要完整也要有一定程度的细致，最后以 HTML 页面形式呈现。

此前用提示词尝试过，但**不同 AI 的输出内容与视觉差异较大**。因此本轮的目标不是写一段更好的提示词，而是把**视觉样式与结构模板固定下来**，并对知识做类型划分，不同类型对应不同结构。

## 二、目标定位（用户已确定）

1. **用途**：个人的速查词典，相当于个人的维基百科。（用户 2026-10-11 明确）
2. **深度**：达到 `_sandbox/nutrition-atlas.html` 这种深度，但部分内容会调整；内容至少分层级：一页入门 / 全面了解 / 深入掌握。
   **实现方式已确认（2026-10-11）**：一份内容 + 深度标记 + 三种视图。同一句话只写一次，视图切换时控制显隐与折叠；不采用「三份独立文档」方案。
3. **与 101Tips 的关系**：101Tips 是早期想法，因太容易漂移，用户打算重新开始该项目，分两步走——先搭以 101Tips 为目的的输出 skill，但**不做绝对限制**，产物既可录入 101Tips 也可单独使用。若 101Tips 后续做了模块化拆解，则考虑先出完整单文件、录入时再做模块化改造。**用户明确表示这部分只是目标，具体细节暂不讨论。**
4. 结论：skill 的**第一版边界定为产出端**（生成 + 完整单文件呈现），收纳端（101Tips 改造）不在第一版内。

## 四、关键判断

1. **症结不是提示词不够严格，而是内容与呈现被揉进同一份 HTML**。每个 AI 都要把结构、样式、文案重写一遍，漂移是必然结果。要消除漂移，知识内容必须有独立的数据形态（单一事实来源），页面由固定渲染层生成——这是结构保证，而非提示词保证。
2. **由此得到三层结构**：生成器（skill）→ 契约层（内容模型 + 设计令牌 + 组件规范）→ 收纳站（101Tips 及其他消费端）。契约层目前缺失，是本次真正要先定义的东西。
3. **视觉不另起体系**——原建议是把营养学样本的暖纸风并入 101Tips 现有令牌体系，避免生成端与收纳端各自演化。**该判断已被用户推翻（2026-10-11）**：所有既有参考一律舍弃，从零重新起主题；令牌源因此落在生成端，收纳端将来跟随生成端，而不是反过来。详见第十节。
4. **交付形态**：用户要求先出完整单文件，因此第一版渲染产物为自包含 HTML；但其底层应是结构化数据，录入 101Tips 时由同一份数据重新渲染，而不是从 HTML 反向解析。
5. **视觉与结构的固化分三层写死**：设计令牌（颜色 / 字体 / 间距 / 圆角）→ 组件库（固定 HTML + CSS 片段，生成时是抄而不是临场设计）→ 类型骨架（每种知识类型的 section 顺序与必选组件、数量下限）。
6. **个人维基定位曾推导出一组「隐藏要求」**（见第十二节）。该判断在 2026-10-11 被用户部分修正：跨文件关联与全局术语库不做，改为单页自包含 + 页内显式声明。

## 五、知识分型（已定，2026-10-11）

### 5.1 切分口径

**领域作标签，性质作骨架。** 学科领域（营养学、物理学）只用于归档与检索，不决定结构；知识性质决定「这一页该长什么样」。

理由：按学科领域切，分类无法穷举、领域彼此交叉，每新增一个领域都可能要多写一套骨架；更关键的是同一领域内不同主题的性质本来就不同——营养学里「营养素分类体系」是概念体系，「如何设计一份减脂餐」是操作流程，「各国膳食指南」是可检索的事实集合，三者不该套同一个骨架。

### 5.2 五类

| 类型 | 知识的形态 | 骨架主体 |
| --- | --- | --- |
| 体系型 | 概念 + 概念间关系 | 知识地图 + 术语体系 + 概念依赖顺序 |
| 流程型 | 步骤 + 判断分支 | 步骤序列 + 决策点 + 失败模式；地图退化为流程图 / 决策树 |
| 清单型 | 可检索的条目集合 | 分类索引 + 条目表 + 别名检索；不需要叙事线 |
| 判断型 | 标准 + 边界 + 取舍 | 判别标准 + 反例 + 争议标注 + 适用条件 |
| 史实型 | 时间 + 因果 | 时间轴 + 因果链 + 分期 + 争议与史料 |

- **史实型为什么独立成类**：营养学的历史只是其中一个模块，删掉不影响骨架；二战史的历史就是全部。属性只能增减模块，无法把时间轴提升为骨架主体——那是类型该管的事。
- **规范型为什么不独立成类**：HTTP/2 协议规范的骨架主体仍是结构（帧格式、状态机、多路复用），落点 = 体系型 + 边界性「有标准法规」，再叠加一个「约束力标注」模块（MUST / SHOULD / MAY）。

### 5.3 五个属性（细化接口）

属性负责处理混合型与后续细化，类型负责确定骨架主体。

| 属性 | 取值 | 触发 / 抑制的模块 |
| --- | --- | --- |
| 主导形态 | 体系 / 流程 / 清单 / 判断 / 史实（可多选，骨架取并集） | 决定骨架主体 |
| 时间性 | 有强演化史 / 历史不重要 | 触发「历史发展脉络」「人物与学派」 |
| 共识度 | 高度共识 / 存在活跃争议 | 触发「争议与不确定性标注」；高度共识则抑制 |
| 量化度 | 定性描述为主 / 数据参数为主 | 触发「量化数据面板」与表格 / 图表承载 |
| 边界性 | 开放学科 / 有标准或法规 | 触发条款式结构与权威来源标注 |

**属性 → 触发的节（2026-10-11 原型落位）**——属性不是抽象标签，每个取值都要能对应到具体节：

| 属性取值 | 触发的节 | 五类中已落位的样板 | 备注 |
| --- | --- | --- | --- |
| 时间性＝有强演化史 | D1 历史脉络 / D2 分期与阶段 | 体系型 D1、史实型 D2 | 史实型的时间轴是骨架主干，不按触发处理 |
| 共识度＝存在活跃争议 | F4 共识与争议 | 体系型、判断型、史实型 | 高度共识时抑制，该节不出现 |
| 量化度＝数据参数为主 | H1 数值参考表 / H2 量化数据面板 | 清单型 H1 | H2 是独立数据面板模块，按需触发 |
| 边界性＝有标准或法规 | 约束力标注（MUST / SHOULD / MAY） | 暂无 | 等「规范型」形态落位后再补 |
| 主导形态 | 决定骨架主体本身 | 全部五类 | 不是触发项，是主键 |

触发的节在原型中显示「属性触发」徽标，悬停可见触发条件；不触发的节不出现，也不留空位。

## 六、深度分层（已定，2026-10-11）

三档：**一页入门 / 全面了解 / 深入掌握**。

实现方式：**一份内容 + 深度标记 + 三种视图**。同一句话只写一次，视图切换时控制显隐与折叠。理由：三份独立文档等于把维护量与漂移风险放大三倍，与本次目标相悖。

## 七、组织粒度（已定，2026-10-11）

用户原话：「目前我只能确定术语可以做成每页自包含，如果相近领域出现同一个重要术语，各自页面都要附带。主题之间我不需要各文件关联，显式声明就可以，用户自己根据前置/相关/跨学科去索引相关内容，可能根据兴趣会延伸出新的主题制作」

结论：

1. **术语**：每页自包含。相近领域出现同一个重要术语时，各自页面都附带完整条目。
2. **不做全局术语库**，不做跨文件双向链接。
3. **主题之间不做文件关联**，只做页内显式声明（前置 / 相关 / 跨学科），由用户自己据此索引；主题按需增量生长，可能由兴趣延伸出新主题。
4. **单页承载**，不做「领域页 + 条目页」两级结构。
5. **风险与缓解**：同一术语在多个页面独立成文，会出现同术语不同定义、不同详略的风险。不靠全局术语库也可缓解——把术语卡的**字段与句式固定进写作规范**（名称 / 英文 / 别名 / 一句话定义 / 展开 / 所属主题），任何一个页面写同一术语都按同一格式。反过来，某术语若在多个页面反复出现，那就是把它升级为独立主题的信号。

## 八、生成流程（已定，2026-10-11）

用户原话：「可以与用户确认深度和边界，比如我刚刚说工程学入门，可能是通用型工程知识和方法论，而非某个具象的门类，不过真正提出需求的时候不一定，需要 ai 主动与我确认」；确认清单方面：「可以，在收集完后还要主动展示提纲与用户确认」。

**skill 是两阶段确认 + 一次生成，共三步：**

1. **确认六项**

   | 确认项 | 问什么 | 不问会怎样 |
   | --- | --- | --- |
   | 范围与切面 | 整体领域、某个分支，还是通用方法论？ | 范围猜错，整页作废或变成空壳模块 |
   | 深度档位 | 默认「全面了解」，还是要一页入门 / 深入掌握？ | 太浅不够用，太深读不完 |
   | 用途与场景 | 做决策 / 能对话 / 系统补课 / 快速查概念？ | 语言风格、假设前提、取舍标准全都偏 |
   | 前置假设 | 默认你已懂哪些基础术语？ | 要么大段解释你已知的，要么直接跳过你需要的 |
   | 类型确认 | 我判断这是「流程型 + 判断型」混合，对吗？ | 骨架主体选错，整页结构不对 |
   | 时效口径 | 写到什么时间点？要不要标注更新速度？ | 快变领域的内容很快过期，且你判断不了 |

2. **展示提纲并确认**：把将要生成的结构摊开——走哪类骨架、包含哪些模块、每模块覆盖什么、数量下限是多少。
3. **生成页面**：按类型骨架 + 属性模块 + 深度标记，输出自包含单文件 HTML。

**范围过大时的三种处理**（不一定是收敛）：

| 处理 | 做什么 | 什么时候用 |
| --- | --- | --- |
| ① 收敛到子领域 | 让用户指定聚焦哪个分支，再按标准流程生成 | 用户其实是想学某个具体方向 |
| ② 换切面 | 不铺分支，改从通用方法 / 思维方式切入（工程学 → 通用工程方法论） | 用户要的是可迁移的思考框架，不是分支清单 |
| ③ 生成分支总览 | 一页学科门类地图 + 各分支入口，每支从简 | 用户想先看全貌，再决定深入哪一支 |

## 九、骨架拼装规则（暂定，2026-10-11）

用户态度：「思路可以，暂定这样，后续实际中在调整」。

骨架分三层拼装，而不是给每类写死一份完整清单：

1. **基线层**：所有类型都有的模块。原型落地时进一步拆成两段——
   - **头部基线**（4 节；清单型因多一个「边界性」入口为 5 节）：A1 一句话定位 → A2 一页纸摘要 → A6 边界声明 → A7 前置门槛清单。
   - **尾部基线**（6 节）：E8 常见误区与陷阱 → I1 学习路线图 → I5 学完能做什么 → J9 相关主题声明 → J10 延伸问题 → J5 来源与参考。
   - 同一个模块在不同类型里**形态不同**：地图在体系型是概念关系图，在流程型是决策树，在史实型是时间轴。
   - 顺序约束只做最小化：A1 打头，A2 与 A6 相邻，A7 在其后；尾部固定为上述顺序；其余节次由类型决定。
2. **类型专属层**：由五类决定，例如流程型的步骤与失败模式、史实型的因果链与分期、判断型的判别标准与反例。
3. **属性触发层**：由五个属性决定，例如「有强演化史」触发历史脉络模块、「高量化」触发数据面板。

**落地方式（2026-10-11，原型已实现）**：每类骨架带一个 `layers` 声明，写明 `head` / `tail` / `attr` 三组节 ID 与每节的触发条件；渲染时据此给每一节打「基线 · 头部 / 基线 · 尾部 / 属性触发 / 类型专属」徽标，并在骨架顶部输出一行**骨架规格校验**（头部与尾部是否完整、位置是否合规、声明的属性触发节是否入骨架）。校验不通过会在页面上直接标红。这是把「骨架从样张变成规格」的第一步——生成端从此有字段可读，不再只看到一段 HTML。

理由：模块池只维护一份，避免五类各写一套造成重复；将来新增类型只需改类型专属层，基线与属性层可复用。

## 十、视觉体系与主题（2026-10-11）

### 10.1 令牌源在生成端

用户决定**舍弃所有既有参考**（101Tips 的 107 个令牌、营养学样本的暖纸风都只作参考，不复用），完全重新起主题。由此确定：生成端是设计令牌的唯一来源，收纳端将来跟随生成端；而不是让生成端去适配 101Tips。这推翻第四节第 3 条的原判断。

### 10.2 三个正交维度

视觉由三个互相独立的维度组合而成：

| 维度 | 管什么 | 实现 |
| --- | --- | --- |
| 主题 theme | 气质：字体族、圆角、留白密度、阴影、背景质感 | 根元素 `data-theme` |
| 配色 palette | 色相：强调色系列与语义色映射 | 根元素 `data-palette` |
| 明暗 mode | 同一套外观的明 / 暗两态 | 根元素 `data-mode` |

三者叠加覆盖 CSS 变量，切换时只换变量、不动版面。分层干净是「加第 N 套主题只是加一份变量表」的前提。

### 10.3 默认主题按知识类型绑定（已定）

- 五类知识各绑定一套默认主题；主题随类型确定，但**允许用户手动更换**。
- **配色是主题内的多组预设**（用户已选）：换配色不破坏主题的字体与质感。
- **混合型**（如「流程型 + 判断型」）取主导类型的主题，另一类用属性模块表达，保证一页一外观。

### 10.4 主题槽位：先设五套，代号占位

用户原话：「主题太少了，先按abcde五套，等到时候主题足够了再来替换」。

含义：先按五套主题建槽位（对应五类，一套一个），**先用 a/b/c/d/e 这样的代号占位，不急于定每套的具体风格**；等主题池积累够了，再逐槽替换为正式主题。

目前已想到的三套候选风格与其适配场景：

| 候选主题 | 底色倾向 | 字形与质感 | 适配场景 |
| --- | --- | --- | --- |
| 暖纸 | 暖米黄（`#F3EEE3` 一类） | 衬线标题 + 无衬线正文，纸纹、描边、印刷感 | 史实型、人文类，需要「档案感」的长文 |
| Claude | 暖白偏米（`#FAF9F5` 一类） | 无衬线为主，大留白、柔和大圆角、弱阴影 | 体系型、说明性内容，读起来要轻 |
| Notion | 冷白到浅灰（`#FFFFFF` / `#F7F7F5`） | 无衬线，小圆角、细边框、高信息密度、几乎无阴影 | 清单型、流程型、技术类，表格与代码多的页 |

注：暖纸与 Claude 同为暖色家族，差异主要在字形与质感（印刷档案感 vs 现代柔和）；若觉得两套过近，可把其中一套换成冷色或深色系以拉开色温。

**待定**：a–e 五套各自最终采用什么风格；每套主题配几组配色、色值如何；Claude / Notion 是品牌名，若将来对外发布需另起内部代号。
