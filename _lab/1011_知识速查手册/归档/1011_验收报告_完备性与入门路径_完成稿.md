## 二、阻断性问题（P0，6 条）

> 判据：会导致模板不可机械使用，或按当前规格生成就会产出错误/不合格页面。

### P0-1　骨架不是「规格」而是「样张」：每个节只有 `id/h/html` 三个字段

- **依据**：`SKELETONS`(342–454) 的每个 section 仅 `{id, h, html}`；`renderSkeleton`(行 464–508) 全量输出、无任何条件分支；讨论稿 §13 待定第 1 项自认「**五类各自的完整骨架：每类含哪些模块、顺序如何、每模块数量下限多少。这才是『结构模板定下来』的主体，尚未展开**」；§4 第 5 条却已经承诺「设计令牌→组件库→**类型骨架（顺序与必选组件、数量下限）**」。
- **影响**：生成端没有任何字段可读，只能照着 HTML 抄结构 → 节数、必选节、每节深度全靠模型自觉，正是 §一 要消灭的「不同 AI 输出差异极大」。同时验收标准里的「数量达标」无法判定（§3.1 行 30），深度三档（P0-5）也无处挂载。
- **改法**：section 升格为规格对象，最小字段集：`{id, hOverride?, layer: baseline|type|attr, req: required|optional, min: {cards?|rows?|chars?}, tier: {basic|full|deep}, trigger?, order}`；五类各附 `meta: {maxSections, basicSections[], defaultThemeSlot, attrs[]}`。「数量下限」要按节定义可数指标：C2 ≥12 条、G2 ≥30 行、E4 ≥5 条、J5 ≥3 条来源。

### P0-2　模块 ID 一号两义（E4、J7），且「常见误区」无 ID

- **依据**：【读到】`MODULES` 行 259 E4 名为「失败模式与常见错误」、when 含判断型、what 称「按严重度列出典型错误」（样例 行 260 无严重度列）；体系型骨架 行 360 把同一 ID 的标题改成「常见误区」；§9 行 198 又把「常见误区」列为**基线层**模块；§3.1 的旧 13 模块清单里它还是独立模块。J7：`MODULES` 行 330 名为「应用案例」，史实型骨架 行 448 改名成「影响与遗产」（语义从「案例」变成「评价」）。
- **影响**：生成端按 ID 取模块会取到语义不同的形态；基线层的「常见误区」在代码里无引用点，五类各自决定要不要写，于是四类直接漏掉；同一页里同名节在两处含义不同。
- **改法**：拆 ID —— 新增 **E8「常见误区与陷阱」**（`layer: baseline`，字段＝误区/为什么这样想/纠正），E4 保留为流程型+判断型的「失败模式（含 severity 列）」，两者禁止互借标题；J7 拆为 **J7 应用案例** 与 **D7 影响与遗产**（史实型专属），并删除 行 448 的标题覆盖。

### P0-3　§9.1 基线层与五类骨架不符（详见第一节表）

- **依据**：§9 行 198 vs `SKELETONS`(344–453) 实际节序。
- **影响**：基线层是「各类型共有」的承诺，破掉之后同一主题在两种类型归属下会得到完全不同的开头与结尾；读者的「找入口」习惯无法跨主题迁移，个人维基的一致性目标失守。
- **改法**：把基线层写成**显式 ID 列表 + 顺序约束**（建议 A1 → A2 → A6 → A7 → [E8 常见误区] → J5，两处待定见 P2-1），并在五类骨架里用 `layer: baseline` 标出，加一条机械校验：生成后基线节必须齐备、顺序必须一致，缺一即报错。

### P0-4　「规范型」路径已定方向，但模块池没有承载模块

- **依据**：【读到】§5.2 行 97 明确「规范型不独立成类：落点＝体系型＋边界性『有标准法规』，再叠加**约束力标注**模块（MUST / SHOULD / MAY）」；§5.3 边界性一栏也写「触发**条款式结构与权威来源标注**」。但 `MODULES` 66 条中**没有任何**承担「约束力等级 / 条款编号 / 标准号与版本」的模块；最接近的 F5「证据与来源分级」(行 273) 是通用溯源，且不在体系型骨架中。
- **影响**：HTTP/2 协议规范这类主题（用户亲自选的 7 个选题之一）会生成一个「学科导论」形状的页面：读者拿不到「这条是 MUST 还是 SHOULD」「对应哪个 RFC 版本」「偏离的后果」，而这正是该类知识的核心价值。
- **改法**：新增 **E9/C8「规范条款与约束力」**（表格：条款 / 级别 MUST-SHOULD-MAY / 适用版本 / 偏离后果 / 出处）与把 **F5 在 `边界性＝有标准法规` 时列为必选**；在属性触发层给出「体系型 × 边界性」的组合示例，不要只留一句描述。

### P0-5　深度三档没有任何载体，而且存在两套互相打架的「分层」

- **依据**：【读到】§2.2 行 20 与 §6（146–150）承诺「一份内容＋深度标记＋三种视图」；§13 待定第 4 项自认「每模块在三档下的详略差异如何表达（哪些字段随档位显隐、哪些是硬下限）」未展开；而 B4「知识分层」的 what（行 211）写「把内容切成核心/进阶/专家三层，对应一页入门/全面了解/深入掌握，**是深度分层的主要载体**」。原型里没有任何 tier/深度字段，也没有视图切换代码。
- **影响**：三种视图的差异无据可依；B4（节内把内容分级）与 tier（节级显隐）是两种完全不同的机制，被同一个词「深度分层」指代，实现时必然冲突；「一页入门」可能变成「把 19 节的正文全塞进去」。
- **改法**：①节级 `tier: {basic|full|deep}` 定义三态＝`整节隐藏 / 摘要化 / 完整`，写进 P0-1 字段；②B4 改名为**「内容重要度分层（核心/进阶/专家）」**并限定它只管节内标号，不管节显隐；③给「一页入门」硬约束：7–10 节、不得出现折叠控件、不得依赖 JS 展开。

### P0-6　类型判定与多类型叠加没有规则，且「人物传记型」零落点

- **依据**：【读到】§5.2 五类表无判定流程与优先级；§5.4 行 144 自认「混合型占比很高」；§8 第 1 步（行 175）只让 AI 说「我判断这是流程型＋判断型混合，对吗？」，没有主轴、上限或节数规则；`SKELETONS` 是单一 `key` 分支（行 464 附近），结构上无法组合。§5.4 的 14 个选题里至少 5 个是混合型（工程学、游戏设计框架、减脂瘦身、docker、HTTP/2）。另：**「人物传记型」在 §5.2 无落点**。
- **影响**：同一主题两次生成可能落入不同类（docker＝流程型 or 清单型），「结构固定」直接失效；混合型若做并集可达 19+16=35 节，先撞上单页承载上限（§三 行 41 已记录营养学样板的折叠与篇幅缺陷）。
- **改法**：①给出**可操作判定流程**：主轴按「读者最终要做的动作」定 —— 执行/操作→流程型，检索/查→清单型，判断/取舍→判断型，理解/建立框架→体系型，知道经过与成因→史实型；②辅类型 ≤1，只允许贡献 ≤3 个模块，不允许重排主轴；③节数上限（建议 20 节，写入 `meta.maxSections`）；④`SKELETONS` 支持 `base + overlay[]`，overlay 只能追加；⑤人志类：人物主题按「主轴＝史实型（生平分期）＋体系型或判断型」处理，并新增 **D4 的扩展形态「生平分期」**（见第五节表）。

## 三、应当补充（P1，12 条）

> 判据：影响质量、会造成同类主题质量参差，但模板仍可先跑起来再迭代。

### P1-1　属性触发层只停留在文档里，代码中几乎没落地
- **依据**：【读到】§9 行 198 承诺三层拼装；实际只有体系型的 D1、F4 标了「· 属性触发」标签，流程/清单/判断/史实四类**零标记**；A5、C6、H2、H4 的样例内容全部是营养学数据（如 4/4/9 kcal、TDEE 活动系数），却**全部不在体系型骨架中**——属性触发在「样例层」演示了，在「骨架层」没生效。
- **影响**：属性填了页面结构也不变，量化度高/强演化史/有争议这些区分全是空转。
- **改法**：五类骨架都补触发节并标 `trigger`；输出一张「属性 → 追加模块」映射表；生成流程第 1 步显式确认属性（不能只确认类型）。

### P1-2　五个属性的区分力不足，且「主导形态」放错了位置
- **依据**：【读到】§5.3(103–109) 五属性＝主导形态 / 时间性 / 共识度 / 量化度 / 边界性。
- **【推断】建议补 5 个真正能区分同类内差异的属性**：①术语量级（大→C3 全局索引，小→C2 卡片）；②标准与版本（有强制标准/版本敏感→约束力标注＋版本号，docker 与 HTTP/2 都吃这个）；③多流派对立（→D5 与 F4 并列，哲学、心理学、经济学必需）；④需计算/推导（→C6＋H2＋E3 数值示例，统计、金融、工程必需）；⑤场景取向（动手 vs 决策，决定 E 族与 F 族的权重）。另：「主导形态」实质是**类型判定的输出**，与被判定的对象放在同一层会循环定义，建议移出属性列表。
- **影响**：同类内差异全靠模型自觉，同一类型下优质页与劣质页的差距不会被模板兜住。

### P1-3　18 个模块零使用；且原 13 模块中 3 项在新模板里「回退消失」
- **依据**：【读到】零使用 = A3 A4 A8 B2 B8 C3 C6 C7 G4 H2 H4 I3 I4 J1 J2 J3 J6 J8。§十一 行 246 明确原型的作用是「用户据此留下/删除/补充」，§13 待定第 2 项仍未定。**回退项**：§3.1 旧 13 模块清单里的「思考模式与心智模型」＝C7、「当前前沿与趋势」＝J1、「跨学科关联」＝J8，在五类骨架中**零落点**（§15 只记录了 A7、J9、J10 三处升级，没有处理这三项）。
- **影响**：新模板在「心智模型 / 前沿 / 跨学科」三个维度上比原来那份 157 行提示词更弱，而这三项恰是个人维基的长期价值项；同时 18 个零使用模块使模块池看起来比实际能力大。
- **改法**：逐个模块给出「保留并规定它至少出现在哪类/哪一档」或「删并并写明理由」；C7 建议放判断型 deep 档、J1 建议全类 deep 档、J8 建议并入 J9 的跨学科关系行。讨论稿可原样保留，但需在 §13 第 2 项结案。

### P1-4　清单型的检索效率、数值口径、索引完备性三个缺口
- **依据**：【读到】条目表 G2 的 when（行 285）承诺「可排序可筛选」，样例是静态表、无任何控件；体检样板全篇**没有「共 N 条 / 覆盖范围」**，而 §7(167 行) 明说清单型「不追求完备、刻意留白」；G2 列＝项目/参考区间/单位，**无「检测方法/口径」列**；C3 术语索引(227) 与 A5 关键数字面板(191) 均未进任何骨架；原型的搜索框只搜模块库、还会强制切回模块库页签（行 534），生成页更不会有页内搜索。
- **影响**：用户对一份体检指标的信任度取决于「表里没有 = 我不需要查」还是「表里没有 = 手册没写」，当前页面会导向后者；缺口径列会让同一指标在不同机构的参考区间被误读为「手册写错了」。
- **改法**：①新增「条目总量与覆盖范围」字段（放 H3 或 A8）；②G2 增 `口径/方法` 与 `数据来源` 列，H1 增 `精度/有效数字`，把「数值＋单位＋口径＋数据时点」定成四元组，并让「数据时点」独立于 J4 时效（J4 现在不在清单型骨架里）；③把「页内搜索框＋表头排序」列为清单型硬要求（原生 `<input oninput>` + `<table>` 过滤约 20 行 JS，仍在单文件零依赖约束内）；④C3 在术语 ≥30 条时触发。

### P1-5　流程型的决策点、失败模式、可执行性、版本时效
- **依据**：【读到】B5「流程图：本次流程的可视化骨架」(213) 与 E1「步骤流程：本次流程的可执行细节」(255) 在 docker 骨架里**相邻出现（B5→E1），同一流程画两遍**；E4 的 what 要求「按严重度」，样例（260）只有现象/原因/处理；docker 骨架里没有「环境与版本前提 / 耗时 / 权限与磁盘前提」的任何落点（补库、装 CI、磁盘不足、权限这些真实卡点只在 J10 延伸问题与 J4 时效里偶然提到）；A7 只写「了解命令行基础」就进入 16 节 docker 命令，读者在「先补命令行」和「继续」之间分叉；C2 术语卡在流程型骨架里**不出现**，image/container/卷/层 这类岗位术语被当常识使用。
- **影响**：零基础读者在 E1 第一节就会卡在术语与前提上；失败模式不标严重度，读者无法判断「这个坑会不会毁数据」。
- **改法**：①B5 与 E1 二选一为必选，另一个降为可选并限定用途（≥8 步时 B5 给全景、E1 给可执行细节，禁止同页同时完整展开）；②E4 增 `severity` 列（阻断/数据损坏/性能/体验）；③新增「环境与版本前提」模块（工具版本、权限、网络磁盘前提、耗时量级）；④流程型把 C2 提为必选且 ≥5 条；⑤A7 增分支句「不满足前置时：先补 X（预计 Y 小时），或跳到第 N 节」。

### P1-6　体系型的概念依赖、术语体系、理论边界

### P1-11　术语跨页一致性的缓解措施没有载体；J6 与 §12 冲突

- **改法**：①把「术语卡写作规范」落成一份可见载体（独立文档或 HTML 内数据规范）：字段名、英文大小写、别名分隔符、一句话定义句式、必须填写所属主题；②J5 强制增加 `lastReviewed` 字段，把「修订时间保留」做进 J5，而不是依赖零使用的 J6；③若允许对齐，另立一份**不在页内**的「术语账本」手工维护，这不违反「页内自包含」。

### P1-12　样例与 what 的承诺不一致，且页面上有可见的占位硬伤
- **依据**：【读到】①D4 首行错误占位行（行 246）；②I1 的 what 承诺「可打勾记录进度」，样例是 `<ol class="steps">` 无勾选控件（307–308）；③E4 的 what 承诺按严重度，样例无该列（259–260）；④G2 的 what 承诺可排序可筛选，样例是静态表（285）；⑤全文含 34 处「示例/占位」文案，若不替换会直接漏入成品。

## 五、专题：Q1 类型划分是否站得住

**结论：【推断】五类作为「性质骨架」是站得住的，缺的是判定口径与三个具体形态的落点。**

【读到】§5.2(88–94) 的五类划分依据是「读者拿这份页面要做什么」，这个口径本身清晰；§5.4 用 14 个真实选题做过验证，覆盖面不错（学科、技能、速查、决策、历史各有点）。史实型独立成类的理由（行 96，删掉历史营养学骨架不塌、二战史历史即全部）是一个可操作的判据。规范型不独立成类、走「体系型＋边界性属性」的方向也合理。

问题出在三处：**①判定过程没有写出来**（只有结果表和一句「我判断这是 XX 型，对吗」）；**②混合型没有叠加规则**（P0-6）；**③三个形态没有落点**。

| 形态 | 材料中的落点 | 骨架适配情况 |
| --- | --- | --- |
| 法规 / 标准型 | §5.2 行 97 明确：体系型 + 边界性属性 | 路径已定但模块缺失：无「约束力标注 MUST/SHOULD/MAY」「条款式结构」「权威来源标注」（见 P0-4） |
| 纯技能型（游泳、演讲、写作） | 未讨论；按性质应归流程型 | 不适配：流程型假设「可执行命令链＋失败模式」，缺「练习—反馈—纠错循环」与自查标准（I3 练习存在但零使用） |
| 数据 / 统计型 | 未讨论；按性质应归清单型 + 量化度 | 部分适配：H1–H4 承载数值，但缺口径/精度/数据时点，指标间计算无落点（C6 未进任何骨架） |
| 人物传记型 | 无落点 | 无对应骨架：史实型主轴是时间轴＋分期＋因果链，D4 人物表承载不了「生平分期＋思想演变＋关系网络」 |
| 语言 / 词汇型 | 未讨论；词汇表→清单型，语法体系→体系型 | 不适配：缺「难度/词频分级」与产出型练习；发音音频与「零外部依赖单文件」相冲，需显式声明不做 |

**建议的判定口径（可直接写进讨论稿 §5.2 与生成流程第 1 步）：**

1. **主轴判据**：问「读者合上页面后要做的第一件事是什么」——要执行→流程型；要查→清单型；要下决定→判断型；要建立理解框架→体系型；要知道经过与成因→史实型。
2. **两栖处理规则**：允许一个辅类型，但必须满足三条硬约束 —— 辅类型只贡献 ≤3 个模块、不得重排主轴节序、总节数 ≤20。判定结果必须写成「主轴＋辅类型＋触发属性」三件套，不允许只写类型名。
3. **三个易混对的裁决**：docker（流程 vs 清单）→ 主轴＝流程（读者要执行），E7 速查表作为辅类型产出；体检指标（清单 vs 数据）→ 主轴＝清单，量化度属性拉高而非改类；人物传记（史实 vs 体系）→ 主轴＝史实（生平分期），思想体系作为辅类型用 C1/C2 落地。
4. **必须写明「不做」的形态**：语言词汇的发音、图表型数据的交互联动等，与「零外部依赖单文件」冲突，应在 §13 明确不做，否则每次生成都会重新纠结。

## 九、总体判断

**总体判断**：模块维度的覆盖已相当完备（66 个模块、十族、五类各有完整样板），但契约维度仍停在样张阶段：骨架与模块的层次归属、数量下限、深度归属都不可机读。若把「可直接投用」定义为生成端能据规格机械拼装，我的估算约为 **55–65%** —— 设计判断的达成度高，契约字段与判定规则接近空白。

**从「不可投用」到「可投用」的五步（按依赖顺序）：**

1. **骨架规格化**：每个 section 补 `layer` / `req` / `min` / `tier` 四个字段，使骨架可机械拼装、可验收。
2. **模块 ID 语义唯一化**：拆出「常见误区与陷阱」「影响与遗产」，锁定一 ID 一语义。
3. **基线层与属性层落地**：基线层写成显式 ID 与顺序约束；属性触发模块写进五类骨架并标注条件。
4. **类型判定与叠加规则**：给出可操作的判定流程、混合型主轴上限与节数上限。
5. **深度三档载体**：节级三态 + 表格摘要化定义 + 隐藏节依赖校验。

**完整性**：好。66 个模块覆盖了定位、地图、术语、演化、操作、判断、检索、量化、自测、元信息十个面，五类各有可运行样板，且 §15 记录了三处缺口如何被补上（A7 矩阵化、J9 五类关系、J10 新增）—— 这个「原型→发现缺口→回写设计」的循环是这份材料最扎实的部分。**我没有发现任何一类知识在模块层面「无话可说」**；问题集中在「规格层」。

**详尽度**：内容层详尽（讨论稿 322 行，调研、论证、取舍理由都留档，符合仓库 SOP「拿这份讨论稿别人能看懂当初为什么这么定」）；**设计层不均衡** —— 分型与视觉的论证很细，而**骨架规格、深度三档、属性落地这三块，正是「结构模板定下来」的主体，全部停留在待定**（§13 第 1、2、4 项）。这不是偶然：材料把最多篇幅给了「为什么这么分」，最少的给了「分完之后字段长什么样」。

**距离可直接投用还差什么**：就是上面五步，按依赖顺序做即可 —— 第 1 步（骨架规格化）是其余四步的载体，应先做；第 2 步（ID 唯一化）与第 3 步（基线/属性落地）可以在原型上直接改；第 4、5 步是纯新增规则，写进讨论稿即可。**第 1 步完成后，建议用清单型和史实型这两个「最不典型」的类型做端到端试生成**（它们各自踩中「表格不可摘要」与「时间线三处重复」两个最大风险点），一试就能暴露剩下的规格漏洞。

**必须由用户判断的三处（评审给不出结论）**：①一页入门是「节内摘要」还是「整节保留」（决定 tier 语义，会反向影响骨架设计）；②三视图是一个 HTML 内切换还是三个文件（影响归档与命名规则）；③原型里没有 `data-theme`/`data-palette` 是否有意留白。

**本次验收未做且建议后续补的**：在浏览器中实际打开原型走一遍交互（特别是搜索强制切页签这一行为在真实使用中的体感）；用一份新主题按现有流程试生成一页，实测 §8 三步是否够用。这两项都需要动手执行，超出本次只读验收的范围。
